사업소득 수정신고 프로세스 개선안

수정신고는 어려운 업무가 아니라 옮겨 적는 일이 많은 업무입니다. 같은 숫자가 품의서 → 구글시트 → ERP → 홈택스까지 네 번 이동하고 시스템마다 요구하는 형식이 모두 달라, 담당자의 숙련도와 무관하게 전사 단계마다 오류가 들어갈 틈이 생깁니다.

대상 업무 사업소득 수정신고(간이지급명세서·지급명세서) 구성 6장

개요 — 그대로 쓸 수 있는 초안

사업소득 수정신고 업무는 재무회계실의 부인 신청 품의를 받아 ERP(옴니이솔)의 소득 데이터를 정정하고, 국세청 홈택스에 간이지급명세서와 지급명세서를 수정신고한 뒤 결과를 회신하는 일련의 과정이다. 이 과정에서 동일한 소득금액·소득세·지방소득세가 네 개의 시스템을 거치며 반복적으로 옮겨 적히고, 각 시스템이 요구하는 입력 형식(열 배치·셀 서식·데이터 타입·파일 분리 단위)이 서로 달라 전사(轉寫) 단계마다 값이 어긋날 여지가 있다.

특히 담당 인력이 8~16주 근무하는 인턴으로 운영되어, 업무 숙련도가 축적되기 전에 인수인계가 반복된다. 절차가 길고 예외 규칙(연도별 세액 특례, 후속 신고 의무 등)이 많아 온보딩 기간이 길어지고, 숙련되지 않은 상태에서 세무 신고 데이터를 다루게 되는 구조적 위험이 존재한다.

개선의 방향은 자동화 자체가 아니라 판단과 전사의 분리다.
사람이 반드시 해야 하는 판단만 남기고, 기계가 더 정확한 일은 도구가 맡는다.

본 개선안은 업무를 사람이 판단해야 하는 영역(ERP상 기존 소득 조회·확인, 부인 대상 검증)과 기계가 더 정확하게 처리할 수 있는 영역(전사, 금액 계산, 서식 변환, 후속 절차 판단)으로 분리하고, 후자를 도구로 대체하는 것을 골자로 한다. 이를 통해 오류 발생 지점을 줄이고, 신규 담당자가 절차를 외우지 않아도 정해진 순서대로 업무를 완료할 수 있는 환경을 마련하고자 한다.

아울러 취급 데이터에 주민등록번호가 포함되는 점을 고려해, 모든 처리는 담당자 PC의 브라우저 내에서만 이루어지고 외부 서버로 전송되지 않는 구조로 설계하였다.

목차 — 장별 핵심 메시지와 담을 내용

1

개요

이 업무의 본질은 정확한 전사이며, 지금은 그 전사를 사람이 하고 있다.

  • 1.1 추진 배경 — 수정신고 업무의 성격, 담당 인력 운영 구조(단기 인턴)
  • 1.2 개선 목표 — ① 데이터 정합성 확보 ② 처리 시간 단축 ③ 온보딩 기간 단축
  • 1.3 개선안 요약 — 판단·전사 분리 원칙과 도구 도입 개요 (1페이지 요약)
쓰는 요령
  • 결재자가 1.3만 읽어도 전체를 파악할 수 있게 요약을 앞에 배치
  • 목표는 정합성을 첫 번째로 — 시간 단축은 부수 효과로 서술해야 세무 업무 성격에 맞음
2

현황 분석

데이터가 어디를 거쳐 가는지 그리면, 오류 지점이 그림 위에 드러난다.

  • 2.1 업무 흐름 — 품의 수신 → 시트 정리 → ERP 정정 → 홈택스 신고 → 재무 회신
  • 2.2 데이터 이동 경로 — 동일 금액이 거치는 4개 시스템과 각각의 요구 형식
  • 2.3 단계별 소요 시간과 반복 횟수 — 건당 소득자 수 × 월 수 = 실제 처리 건수
구간옮기는 대상요구 형식
품의 → 구글시트소득자·월별 금액시트 H~AC 배치 (중간에 S·T·U 삽입)
ERP → 구글시트소득자코드, 기존 소득금액이름 셀 내 줄바꿈 표기, 6자리 코드
구글시트 → ERP최종 소득금액전 셀 텍스트 서식, 소득자코드로만 식별
구글시트 → 홈택스최종 소득금액컬럼별 타입 상이(숫자·문자 혼합), 귀속월별 파일 분리
근거 자료
  • 기존 관리 시트에 기록된 구간별 소요 시간 메모(예: “1칸 1분”, “2칸 2분 4초”)를 인용하면 정량 근거가 됨
  • 실제 처리량 예시: 관리 시트 누적 121건의 소득자 그룹, ERP 반영 대상 708행
3

문제점 — 오류 발생 지점

개인의 부주의가 아니라 구조가 만드는 오류다. 유형별로 나눠 제시한다.

  • 3.1 전사 구조상의 오류 — 붙여넣기만으로 완결되지 않는 열 배치
  • 3.2 조회·계산 오류 — 수기 조회와 수기 계산
  • 3.3 형식 오류 — 시스템별 상이한 입력 규격
  • 3.4 절차 누락 — 조건부로 발생하는 후속 의무
  • 3.5 인력 구조상의 제약 — 단기 근속과 반복되는 온보딩
유형구체적 사례결과
전사품의 파일마다 열 배치가 다름(기사코드 열 유무). 시트 중간에 S·T·U가 있어 한 번에 붙여넣을 수 없음열 밀림·값 어긋남
조회소득자코드를 ERP에서 1명씩 조회해 이름 옆에 수기 입력오타 시 다른 소득자에게 신고
계산최종금액 = 기존 + 부인 을 수기로 계산금액 오신고
형식ERP는 전 셀 텍스트, 홈택스는 컬럼별 타입 상이·귀속월 앞자리 0 유지업로드 검증 반려·재작업
누락전년도 이전 소득이면 지급명세서(연별) 후속 신고 필요 / 특정 기간 세액 0원 규칙신고 누락·오신고
인력8~16주 근속, 예외 규칙이 다수숙련 전 이직, 온보딩 반복
서술 시 주의
  • “담당자가 실수했다”가 아니라 “구조가 실수를 유발한다”로 서술 — 개선안의 설득력이 달라짐
  • 소득자코드는 중복 불가(Unique) 값이라는 점을 명시하면 오류의 심각도가 전달됨
4

개선 방안

전사를 없애고, 사람은 확인과 판단만 한다.

  • 4.1 기본 원칙 — 판단(사람) / 전사·계산·서식(도구) 분리
  • 4.2 도구 구성 — 품의 판독 · 코드 사전 · 자동 계산 · 양식 생성 · 진행 관리
  • 4.3 개선 후 업무 흐름 — 사람이 하는 일이 무엇만 남는지 대비 제시
  • 4.4 데이터 보안 설계 — 주민등록번호 취급 원칙, 외부 전송 없음
  • 4.5 오류 방지 장치 — 규칙을 도구가 먼저 점검
문제개선남는 사람의 일
품의 내용 수기 전사품의 파일 업로드 시 자동 판독(열 배치 자동 인식)내용 확인
소득자코드 수기 조회주민번호 기준 코드 사전에 축적·자동 적용신규자만 조회
최종금액 수기 계산기존 + 부인 자동 계산, 세액 자동 산정기존 소득 조회·입력
업로드 양식 수기 작성ERP·홈택스 규격에 맞춰 자동 생성, 홈택스는 귀속월별 자동 분리업로드·검증
진행 상태 수기 관리건별 진행 체크리스트, 후속 신고 필요 여부 자동 판정완료 확인
4.5에 넣을 오류 방지 장치
  • 전년도 이전 소득 포함 시 지급명세서 후속 신고 필요 자동 안내 / 미해당 시 “해당 없음” 처리
  • 특정 기간 세액 0원 규칙 위반 값 경고
  • 소득자코드 누락·기존금액 미입력 칸 수 표시 → 미완 상태로 파일 생성 방지
  • 동일 소득자·동일 귀속월 중복 시 합산(홈택스는 소득자별 1행 원칙)

  • 실제 업로드 검증 통과 여부를 확인했다면 그 결과를 반드시 추가
6

기대 효과 및 실행 계획

효과는 정합성 → 시간 → 온보딩 순으로. 도입은 병행 운영부터.

  • 6.1 기대 효과 — 정합성 / 처리 시간 / 온보딩 기간
  • 6.2 도입 계획 — 1단계 병행 운영 → 2단계 전환 → 3단계 정착
  • 6.3 리스크 및 대응 — 도구 오류 가능성, 검증 절차 유지
  • 6.4 향후 과제 — 미해결 영역
구분현재개선 후
정합성전사 4구간 전부 수기수기 입력은 ERP 조회값 1종만
처리 시간(측정값 기입)(측정값 기입)
온보딩매뉴얼 숙지 후 절차 암기 필요화면 순서대로 진행, 규칙은 도구가 점검
6.3 리스크 — 반드시 넣을 것
  • 도구도 오류가 있을 수 있으므로 업로드 전 검증 절차는 그대로 유지한다고 명시
  • 도입 초기에는 기존 방식과 병행 운영하며 결과를 대조
  • 담당자 변경 시 인수인계 항목(장부 파일 위치, 코드 사전) 명시
6.4 향후 과제 — 솔직하게 남길 것
  • 지급명세서(연별) 수정신고의 대조 검증은 아직 수기 — 자동화 여지 있음
  • ERP 기존 소득 조회는 시스템 접근 권한이 필요해 현재 자동화 불가
  • 다수 담당자 동시 편집은 파일 기반 관리의 한계

작성 전에 채워야 할 것

  • 소요 시간 측정값 — 개선 전/후를 같은 기준으로. 기존 시트에 남겨둔 구간별 시간 메모가 출발점이 됩니다. 1건(소득자 1명 × 월 n건) 기준으로 재보는 것이 가장 설득력 있습니다.
  • 과거 오류 사례 — 실제로 재작업이 발생했던 건이 있다면 익명화해 1~2건. 문제의 심각도를 보여주는 가장 강한 근거입니다.
  • 연간 처리 건수 — 개선 효과를 연 단위로 환산할 때 필요합니다.
  • 실제 업로드 검증 통과 여부 — ERP·홈택스에 실제로 올려 검증까지 통과한 결과. 5장의 신뢰도를 좌우합니다.
이 문서는 개선안 작성을 위한 설계안입니다. 각 장의 표와 수치는 실제 데이터를 대조해 확인한 값으로, 본문 작성 시 그대로 인용할 수 있습니다. 측정값이 필요한 항목은 위에 별도 표시했습니다.
